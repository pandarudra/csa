# SpotifyCares Support Agent

An AI support agent for **SpotifyCares** (Twitter/X), built on the
[Customer Support on Twitter](https://www.kaggle.com/datasets/thoughtvector/customer-support-on-twitter)
dataset. Given an incoming customer message, it:

1. **Classifies** the message into one of 6 intents derived from the real
   SpotifyCares data (see `intents.yaml`).
2. **Drafts a reply** grounded in how SpotifyCares has historically resolved
   similar issues (semantic retrieval over ~4,000 reconstructed conversations).
3. **Decides** `auto_handle` vs `escalate`, with a stated reason.

See `report/REPORT.md` for problem framing, baseline comparisons, failure
analysis, and an honest look at what the headline numbers don't tell you.
See `report/DECISIONS.md` for the non-obvious engineering calls and why.

## Architecture

```
raw TWCS export (3M tweets)
   -> src/data_prep.py         thread reconstruction, brand filter, subsample
   -> data/processed/spotify_threads.jsonl   (4,000 threads, committed)
   -> src/eda_taxonomy.py      embed + cluster customer messages (dev-time only)
   -> intents.yaml             6 intents, hand-named from real clusters
   -> src/label_tool.py        hybrid human+LLM-assisted golden-set labeling
   -> golden/golden_set.csv    150-250 hand-confirmed examples
   -> src/retrieve.py          builds the cached semantic retrieval index
   -> data/processed/retrieval_index.{jsonl,npy}

live message
   -> src/pipeline.py (SupportAgent)
        classify (LLM) -> retrieve (embeddings) -> draft reply (LLM) -> escalate (rules + LLM)
   -> structured AgentResult

src/baselines.py    trivial + simple (no-LLM) baselines, for fair comparison
src/eval_harness.py metrics, LLM-as-judge, judge/human agreement -> results/
src/llm_client.py   thin NVIDIA NIM (OpenAI-compatible) wrapper, used by everything above
```

## Setup

Requires Python 3.12+ and a free [NVIDIA NIM](https://build.nvidia.com/) API key.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # then edit .env and set NVIDIA_API_KEY
```

## Dataset preparation

The raw TWCS CSV (~493MB, ~3M rows) is **not** committed to this repo (see
`.gitignore`) -- download it from Kaggle
([`thoughtvector/customer-support-on-twitter`](https://www.kaggle.com/datasets/thoughtvector/customer-support-on-twitter))
and place it at `dataset/customer-support-on-twitter/twcs/twcs.csv`.

```bash
python -m src.data_prep
```

This reconstructs SpotifyCares conversation threads (walking the reply
chain in the raw export), drops a handful of viral-broadcast-tweet outliers
(see `report/DECISIONS.md`), and writes a deterministic 4,000-thread sample
to `data/processed/spotify_threads.jsonl` -- **this file is committed**, so
`run_eval.sh` does not require the 493MB raw file to reproduce results.

## Intent taxonomy

`intents.yaml`'s 6 intents were not guessed upfront -- they came from
embedding 1,200 real customer messages and k-means clustering them
(`python -m src.eda_taxonomy`), then manually inspecting and naming the
resulting clusters. See the comment block at the top of `intents.yaml` for
the two merge decisions (family-plan issues and ads-on-premium) and why.

## Golden set

`golden/golden_set.csv` (150-250 examples) was built with hybrid labeling:
a human labels a ~45-example seed set with no model assistance, then an
LLM drafts suggestions for the rest using that seed set + a written rubric
(`golden/labeling_rubric.md`) as context -- every suggestion is reviewed
and explicitly accepted or edited by the human before being written, never
accepted silently. See `golden/sampling_notes.md` for exactly how sampling
and labeling went, and the label provenance actually recorded.

To (re)build it:

```bash
python -m src.label_tool
```

Resumable -- progress is saved after every example; re-running picks up
where you left off.

## Running the agent

```bash
python scripts/run_pipeline_demo.py "I can't play any songs on Premium, it just spins forever"
```

Prints the classified intent, the historical cases retrieved as grounding,
the drafted reply, and the auto_handle/escalate decision with its reason.

## Running evaluation

```bash
bash scripts/run_eval.sh
```

Runs the trivial baseline, the simple (no-LLM) baseline, and the full
agent over the same held-out golden **test** split, plus LLM-as-judge
reply-quality scoring, and writes everything to `results/`. Requires
`golden/golden_set.csv` to already exist (labeling is a one-time,
human-in-the-loop step -- see above -- and is not regenerated by this
script).

Judge/human agreement (the assignment's mandatory evidence that the LLM
judge is trustworthy) is a short separate interactive step, not run by
default:

```bash
python -m src.eval_harness --human-judge      # you score ~40 of the same replies
python -m src.eval_harness --judge-agreement  # compares your scores to the LLM judge's
```

## Metrics

Headline numbers live in `results/metrics.json` after running
`scripts/run_eval.sh`, and are reported with full context (baselines,
failure modes, and what's misleading about them) in `report/REPORT.md` --
not restated here, so this file never drifts out of sync with the actual
generated results.

## Reproducing results

1. `pip install -r requirements.txt`, set `NVIDIA_API_KEY` in `.env`.
2. Golden set and retrieval index are already committed/cached for you
   (`golden/golden_set.csv`, `data/processed/`) -- `bash scripts/run_eval.sh`
   reproduces the headline metrics from there in well under 15 minutes.
3. To rebuild from scratch instead (raw dataset required): `python -m
   src.data_prep && python -m src.retrieve && python -m src.label_tool`
   before `run_eval.sh`.

## Design decisions & limitations

See `report/DECISIONS.md` for the full list of non-obvious calls (why
NVIDIA NIM instead of the originally-planned Gemini, why a flat NumPy

headline number" section for the limitations that matter most.
